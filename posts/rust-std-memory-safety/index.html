Rust’s adoption has accelerated in the agentic era, and two forces are pushing in the same direction.

Memory-safety bugs now become exploits in hours. AI has collapsed the time between finding a bug and exploiting it. The median time from a vulnerability’s discovery in the wild to its weaponization is now well below 24 hours, while enterprises can take 30 to 60 days to fix critical exposed systems. When a memory-safety bug can be weaponized that quickly, preventing it in the first place matters more than ever.

Rust’s compiler gives agents, and people, the confidence to change code. Rust’s rich type system and ownership model encourage good designs while ruling out whole classes of safety issues, so large refactors become routine rather than risky. Rust developers like to say that if it compiles, it works: change a type, follow the compiler errors, and the program usually works again once they’re gone. Agents benefit from the same loop.

Microsoft made Rust a Tier-1 internal language alongside C++, C#, and TypeScript, and GitHub rewrote the Copilot agent runtime in Rust. Other projects moving to Rust include Bun, Android, the Linux kernel, and Cloudflare.

With so much critical code moving to Rust, we wanted a closer look at the code everything else builds on: the standard library. This year, FORGE Lab spent some time exploring it and came across a few interesting memory-safety bugs. Rust’s popularity wasn’t the only reason we looked. We write many of our internal tools in Rust and genuinely enjoy using it, and our team includes the authors of Rudra, a static analyzer that found memory-safety bugs across the Rust ecosystem in 2021 and led to 76 CVEs.

In this post, we share some of the bugs we reported to the Rust issue tracker. We use them to discuss what Rust does and doesn’t guarantee, why writing correct unsafe Rust is so difficult, and why Rust’s safety model still matters even though its memory safety isn’t perfect.

Patterns of Rust’s Safety Bugs

At the lowest level, Rust uses unsafe blocks to work with raw pointers and interact directly with the operating system. Much of the standard library, including Vec and String, is built from small unsafe pieces wrapped in safe APIs. Inside an unsafe block, the programmer takes responsibility for the guarantees the compiler can’t check, and that responsibility extends to the safe API built around it. That API must be sound: no matter how safe code uses it, it must be impossible to trigger undefined behavior.

Upholding that promise is harder than it looks. Consider a function that returns the byte at idx from any type that can be viewed as a byte slice, skipping the redundant bounds check after doing its own:

pub fn get<S: AsRef<[u8]>>(s: &S, idx: usize) -> Option<u8> {
    if idx < s.as_ref().len() {
        // SAFETY: we just checked that `idx` is in bounds.
        Some(unsafe { *s.as_ref().get_unchecked(idx) })
    } else {
        None
    }
}

The hard part of unsafe Rust is knowing what you can trust. The function above looks correct, but it assumes that two calls to as_ref return the same slice. Because S is chosen by the caller, a safe AsRef implementation can return a long slice the first time and an empty one the second, and get reads out of bounds. Unsafe code must be careful with every call it makes, and the bugs we found fall into three patterns of misplaced trust: trusting code not to panic, trusting user-provided implementations to be correct, and trusting the underlying system.

Pattern 1: Trusting code not to panic

Unsafe code often breaks an invariant for a moment and restores it afterward; for example, it may allocate an uninitialized buffer and fill it directly, avoiding redundant writes to zero the memory first. That’s fine as long as the function runs to the end. But many operations in Rust can panic, from out-of-bounds indexing to calls into user-provided code, and by default a panic unwinds: it leaves the function early while still running destructors. Unwinding inside that window becomes an invisible exit that exposes the broken invariant to code that trusts it. Bugs of this kind are called panic safety bugs.

MapWindows::clone

Let’s look at one of our bug reports, a panic safety issue in MapWindows::clone. Iterator::map_windows, a nightly API, yields overlapping windows of N items. It keeps the current window in a Buffer whose destructor drops the N items starting at start. In Rust 1.97.0, library/core/src/iter/adapters/map_windows.rs defines it as:

37struct Buffer<T, const N: usize> {
38    // Invariant: `self.buffer[self.start..self.start + N]` is initialized,
39    // with all other elements being uninitialized. This also
40    // implies that `self.start <= N`.
41    buffer: [[MaybeUninit<T>; N]; 2],
42    start: usize,
43}

Buffer::clone, in the same file, built the new buffer first and filled it afterward:

195impl<T: Clone, const N: usize> Clone for Buffer<T, N> {
196    fn clone(&self) -> Self {
197        let mut buffer = Buffer {
198            buffer: [[const { MaybeUninit::uninit() }; N], [const { MaybeUninit::uninit() }; N]],
199            start: self.start,
200        };
201        buffer.as_uninit_array_mut().write(self.as_array_ref().clone());
202        buffer
203    }
204}

After line 197, buffer breaks its own invariant: its slots are uninitialized, but its destructor is already armed. The clone() call on line 201 runs the user’s T::clone before the slots are written. If that call panics, unwinding drops buffer and runs drop_in_place on N uninitialized values. Our proof of concept uses only safe code: an element type whose clone always panics, which crashes when the destructor reads the garbage. The fix holds the new buffer in ManuallyDrop until it is fully written, so unwinding leaks the half-built buffer instead of dropping it.

The general lesson is to treat every call to code you don’t control, such as clone, drop, comparisons, closures, and iterator methods, as a possible early exit. Either finish the work that may panic before breaking an invariant, or make the broken state safe to unwind through: hold it in ManuallyDrop, or use a guard whose destructor restores the invariant, like Vec’s internal SetLenOnDrop. The Rustonomicon covers this under exception safety.

Allocators must not unwind

The recently stabilized allocator API is further evidence of how hard panic safety is to get right. With std, the default response to an allocation failure is to abort the process rather than unwind, so much of the standard library’s unsafe code was written as if allocation never unwinds. Custom allocators can break that assumption, and while the API was being stabilized, reports kept turning up places that would become unsound if an allocator unwound: we reported one in BTreeMap::insert, and others found more (#159334, #159368, #159370). Whether a function can unwind isn’t part of its type, so the compiler can’t point to every place that relies on allocation never unwinding, and fixing them one by one would mean auditing everything that allocates. Instead, the Allocator stabilization, shipping in Rust 1.100 on November 12, requires implementors never to unwind from the trait’s methods or from drop, noting that “unwinding out of many allocation-related methods was found to be a pervasive source of unsoundness.”

Pattern 2: Trusting user-provided implementations to be correct

Unsafe code often calls into code its caller provides: a comparator, a trait implementation, a closure. That code is safe, but safe doesn’t mean correct, and it can return inconsistent or plainly wrong answers. The question is who is responsible when it does. In C++, it’s the caller. std::sort requires its comparator to be a strict weak ordering, and breaking that rule is undefined behavior. With libstdc++, sorting equal elements with <= reads past the end of the vector:

std::vector<int> v(100, 42);
// Bug: `<=` is not a strict weak ordering, since cmp(a, a) is true.
std::sort(v.begin(), v.end(), [](int a, int b) { return a <= b; });
// AddressSanitizer: heap-buffer-overflow in std::__introsort_loop

It’s an easy mistake to make, common enough that libc++ added debug checks for it. The same comparator in Rust is a logic error, not a memory safety bug:

let mut v = vec![42; 100];
// Same bug: this claims `a < b` whenever `a <= b`.
v.sort_by(|a, b| if a <= b { Ordering::Less } else { Ordering::Greater });

sort_by may panic or leave the slice in an unspecified order, but it never causes undefined behavior. In Rust, the responsibility sits with the unsafe code: the comparator is safe code supplied by the caller, so the unsafe code inside the sort must stay sound no matter what it returns. The same goes for every safe trait a user can implement: comparisons can be inconsistent, an ExactSizeIterator can report a length that doesn’t match the items it yields, and Borrow can return a different value on each call.

str::replace with a custom Pattern

Another of our bug reports shows how easy this trust is to miss: str::replace with a custom Pattern can create a non-UTF-8 String. String search APIs accept any type that implements the nightly Pattern trait, and a pattern can describe itself through as_utf8_pattern. str::replace uses that description to take a fast path when replacing one ASCII byte with another. In Rust 1.96.0, the fast path in library/alloc/src/str.rs looked like this:

268pub fn replace<P: Pattern>(&self, from: P, to: &str) -> String {
269    // Fast path for replacing a single ASCII character with another.
270    if let Some(from_byte) = match from.as_utf8_pattern() {
271        Some(Utf8Pattern::StringPattern([from_byte])) => Some(*from_byte),
272        Some(Utf8Pattern::CharPattern(c)) => c.as_ascii().map(|ascii_char| ascii_char.to_u8()),
273        _ => None,
274    } {
275        if let [to_byte] = to.as_bytes() {
276            return unsafe { replace_ascii(self.as_bytes(), from_byte, *to_byte) };
277        }
278    }

replace_ascii, in the same file, then rewrites the bytes:

708unsafe fn replace_ascii(utf8_bytes: &[u8], from: u8, to: u8) -> String {
709    let result: Vec<u8> = utf8_bytes.iter().map(|b| if *b == from { to } else { *b }).collect();
710    // SAFETY: We replaced ascii with ascii on valid utf8 strings.
711    unsafe { String::from_utf8_unchecked(result) }
712}

The CharPattern branch on line 272 checks that the character is ASCII, but the StringPattern branch on line 271 assumes a one-byte string pattern must be ASCII. That holds for &str patterns, but StringPattern stored &[u8], and as_utf8_pattern is a safe method any Pattern can implement. In our proof of concept, a custom pattern reports the single byte 0x80, which only appears inside multibyte UTF-8 sequences:

impl Pattern for NonAsciiBytePattern {
    // ...
    fn as_utf8_pattern(&self) -> Option<Utf8Pattern<'_>> {
        static NEEDLE: [u8; 1] = [0x80];
        Some(Utf8Pattern::StringPattern(&NEEDLE))
    }
}

// "\u{d000}" is [ed, 80, 80]; the result is [ed, 3f, 3f], which is not UTF-8.
let corrupted = "\u{d000}".replace(NonAsciiBytePattern, "?");

str::replace rewrites the continuation bytes and returns a String that isn’t valid UTF-8, and later string operations that rely on UTF-8 reach undefined behavior. The fix changed StringPattern to hold &str instead of &[u8], so the type itself now guarantees UTF-8. In Rust 1.97.0, library/core/src/str/pattern.rs reads:

173pub enum Utf8Pattern<'a> {
174    /// Type returned by String and str types.
175    /// This stores `str` rather than bytes so callers cannot describe
176    /// non-UTF-8 string patterns through this API.
177    StringPattern(&'a str),
178    /// Type returned by char types.
179    CharPattern(char),
180}

When unsafe code depends on a property of a user-provided implementation, don’t take it on faith. Call the implementation once and keep the result, validate what it returns, or encode the property in a type that safe code can’t forge, as this fix did. If none of those work, make the trait unsafe so implementors explicitly promise to uphold it.

More examples

join shows how easy it is to fix this kind of bug only partway. In 2020, we reported that it trusted Borrow::borrow to return the same string on each call (CVE-2020-36323), and the fix handled strings that shrink between calls. In April 2026, the same function needed another fix: join borrows the first element twice, and if it grows on the second call, the remaining-length calculation underflows into a heap overflow. The earlier fix had never covered that path.

The Pattern API has been questioned before. In 2019, a report that trim_start_matches trusted a searcher’s indices was closed because Searcher is an unsafe trait: its implementations promise to return valid indices (#62773). This year showed that promise isn’t enough on its own. In June, a safe Pattern was found to hand back a perfectly valid searcher built for a different string, and consumers such as strip_prefix_of applied its ranges to the original string unchecked, reading out of bounds (#158265). In October, a report pointed out that the contract of the Searcher trait doesn’t spell out what str::split relies on (#164904), and auditing the code around it turned up the same wrong-string problem in split_once (#165076). Both soundness bugs are still open. And during the Allocator stabilization, Arc turned out to trust that a cloned allocator can free the original’s memory, even though anyone can write a safe Clone implementation that breaks that (#156920). The requirement was moved into a separate unsafe marker trait.

Pattern 3: Trusting the underlying system

The first two patterns stay inside Rust code. The third sits at the boundary with the operating system, where unsafe code trusts process-wide state such as signal stacks, memory mappings, and the environment, which other threads, C libraries, or the kernel can touch at any time. These bugs have been hard to find automatically, because a static analyzer would need to model all of that surrounding behavior. AI agents change the picture: they understand enough about the environment the code runs in to make this area practical to search. We started exploring it and found some interesting bugs.

process::exit and the main thread’s signal stack

When a thread overflows its stack, Rust prints a clear message and aborts instead of crashing with a bare segmentation fault:

thread 'main' (3307186) has overflowed its stack
fatal runtime error: stack overflow, aborting

This relies on a few pieces of process-wide state. Each thread’s stack ends in a guard page, an inaccessible region just past the stack’s limit: pthread reserves one for every spawned thread, and on Linux the kernel’s own stack guard plays that role for the main thread. Touching it raises SIGSEGV, and Rust registers a handler for that signal. The handler can’t run on the stack that just overflowed, so Rust also gives each thread an alternate signal stack, a small separate mapping with a guard page of its own, which the kernel switches to when it delivers the signal. The handler checks that the faulting address is inside the guard page, prints the message, and aborts.

We found that calling process::exit from a child thread tears down the main thread’s alternate stack while the main thread is still running. process::exit runs the runtime’s cleanup before calling libc’s exit, and in Rust 1.98.0 that cleanup ends in library/std/src/sys/pal/unix/stack_overflow.rs:

196pub unsafe fn cleanup() {
197    if cfg!(panic = "immediate-abort") {
198        return;
199    }
200    // FIXME: I probably cause more bugs than I'm worth!
201    // see https://github.com/rust-lang/rust/issues/111272
202    unsafe { drop_handler(MAIN_ALTSTACK.load(Ordering::Relaxed)) };
203}

Line 202 passes MAIN_ALTSTACK, the main thread’s alternate stack, to drop_handler:

297// SAFETY: we warned the caller this disables the alternate signal stack!
298unsafe { sigaltstack(&disabling_stack, ptr::null_mut()) };
299// SAFETY: We know from `get_stackp` that the alternate stack we installed is part of
300// a mapping that started one page earlier, so walk back a page and unmap from there.
301unsafe { munmap(data.sub(page_size), sigstack_size + page_size) };

Line 298 disables the alternate stack of the calling thread, but line 301 unmaps the main thread’s. The code assumes it runs on the main thread, which isn’t true when a child thread calls process::exit. The main thread keeps running until libc’s exit finishes, with its signal stack registration still pointing at unmapped memory. If it overflows its stack in that window, the kernel can’t deliver the signal, and our proof of concept dies with a plain segmentation fault instead of Rust’s message. The bug dates back to 2015, and the fix stops cleaning up the main thread’s alternate stack altogether.

We also checked whether this could become a security issue. In theory, it could lead to code execution: if a writable mapping landed at the old alternate stack’s address, the kernel would deliver the main thread’s next signal onto it, and another thread could overwrite the handler’s frame, such as its return address, while it runs. In practice, the conditions are very tight. Everything has to happen in the brief window before libc’s exit finishes, the new mapping must have exactly the right size to reuse that address, and overwriting the frame takes a second race inside a short handler. We found no reliable way to get a writable mapping of that size, so we judged it unlikely to be exploitable. The issue has more details in its security impact analysis.

CommandExt::exec and the global environment

Our other report involves the process environment. On Unix, CommandExt::exec replaces the current process with a new program. When the command has its own environment variables, exec points the process-global environ at a new array, calls execvp, and restores environ if execvp fails. In Rust 1.99.0, Command::exec takes the environment lock in library/std/src/sys/process/unix/unix.rs:

242let _lock = sys::env::env_read_lock();
243
244let Err(e) = self.do_exec(theirs, envp.as_ref());

Command::do_exec, in the same file, then swaps the environment:

409    _reset = Some(Reset(*sys::env::environ()));
410    *sys::env::environ() = envp.as_ptr();
411}
412
413libc::execvp(self.get_program_cstr().as_ptr(), self.get_argv().as_ptr());
414Err(io::Error::last_os_error())

Line 242 takes only the read side of the environment lock, yet line 410 writes the process-global environ; line 409 saves the old value so it can be restored if execvp on line 413 fails. Writing environ under a read lock lets other threads in. A thread calling env::var takes the same read lock and can see variables meant only for the new program, and two failed exec calls racing each other can leave environ pointing at a freed array that a later env::vars_os() reads. Both proofs of concept use only safe Rust. A 2018 fix held an exclusive lock here, but when the environment lock became a read-write lock in 2021, exec kept the read side. A fix that avoids touching environ by calling execve directly is in review.

env::set_var

The environment has caused trouble before. env::set_var was safe to call from Rust 1.0 until the 2024 edition, but on most Unix platforms the C library’s environment isn’t thread-safe, and many C functions read it without going through Rust’s lock, including some that the standard library itself calls for DNS lookups. After a discussion that began in 2015, the 2024 edition marked set_var and remove_var as unsafe. As their documentation now puts it, the only sound option in a multi-threaded program is not to call them at all.

process::exit and thread-local destructors

Getting this boundary right is hard, and more problems are still open. While exploring this area, we independently ran into a double free in safe code that process::exit can cause through thread-local destructors. It was reported by someone else (#164243), but it’s worth mentioning here. libc’s exit first runs the calling thread’s thread-local destructors, as C++ requires, and Rust registers its destructors the same way. If a destructor calls process::exit while a thread local is being replaced, libc drops that thread local a second time. A proposed fix switches process::exit to POSIX _exit, which ends the process without running these handlers.

Limitations, before we continue

Our focus was the Rust standard library: unsafe code behind its APIs that safe code can misuse. Bugs in the compiler itself, such as miscompilations and holes in the type system, were out of scope, though there are plenty of them.

Why Rust still matters

These bugs may look alarming, but most Rust users don’t need to worry about them. Each pattern needs an unusual setup to trigger: a panic that unwinds at exactly the wrong point, a deliberately misbehaving implementation, or an unusual interaction with the operating system, such as calling process::exit from a child thread or racing two failed exec calls. Ordinary Rust code is unlikely to do any of these, and most of the bugs have already been fixed.

It also helps to distinguish a vulnerability in a library from one in an application. Every bug in this post is a soundness bug in the standard library: some safe code could trigger undefined behavior through its API. That becomes a serious application vulnerability only if a real program reaches the API in that unusual way.

Some people argue that Rust’s memory safety doesn’t matter if it isn’t perfect. We think that misses what the safety model gives us: a precise vocabulary for what even counts as a safety bug. Rust’s rule is that safe code must never cause undefined behavior, so when it does, some unsafe code broke its contract, and that code has to change.

Many of the bugs in this post wouldn’t be considered bugs in other languages. A comparator that breaks std::sort is the caller’s fault in C++, and a race between setenv and getenv in C is arguably nobody’s fault. Rust gives us the language to say whose fault it is and what needs to be fixed: join has to stay sound against a misbehaving Borrow, and set_var became unsafe so callers explicitly take on the responsibility. Because the library owns that responsibility, we can fix and prevent these bugs once, at the library level, instead of hoping every application avoids them. That’s what turns each of these reports into a concrete fix rather than a shrug.

Takeaways

If you write unsafe Rust, the three patterns make a short checklist. For every call inside an unsafe region, ask:

  • Can it panic while an invariant is broken?
  • Does it run code your caller supplied?
  • Does it touch state that another thread, a C library, or the kernel can change underneath you?

Knowing what you trust, and why, is most of the work.
